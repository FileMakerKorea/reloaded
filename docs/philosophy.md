이 문서는 초기 논의에서 정한 방향과 그 이유를 기록한다. 구현 완료를 뜻하지 않으며, 구체적인 구현안과 검증 과제는 구분하여 남긴다. 프로젝트 이름은 **PROJECT RELOAD에서 PROJECT RELOADED로 변경**했다. 좋은 개발 철학을 다시 불러와 현재의 표준 기술과 AI로 새롭게 구성한다는 의미다.

## 1. FileMaker의 즉각적인 개발 감각을 현대 웹으로

FileMaker에서 살리고 싶은 것은 화면을 보며 바로 고치고 실행해 확인하는 개발 감각이다. 작은 업무 프로그램을 만들기 위해 개발자가 매번 UI, API, 데이터 모델, 쿼리, 빌드와 배포를 따로 연결해야 하는 부담을 줄인다.

개발 생산성이 좋아도 사용자 증가에 따른 라이선스 부담이 커질 수 있고, 웹의 실행 비용을 낮추더라도 복잡한 개발·배포·유지보수 과정에서 사람의 비용이 커질 수 있다. RELOADED는 개발 시간과 운영 비용을 함께 고려한다.

핵심은 개발 중 객체를 자유롭게 수정하고 즉시 확인하는 것이다. 이를 운영 환경에 모든 변경을 곧바로 배포한다는 의미로 해석하지 않는다.

### 로컬 개발과 운영 배포의 분리

RELOADED의 직접 편집 기능은 로컬 확인용 브라우저에서 실행한다. API와 업무 로직도 로컬 서버에서 실행·검증할 수 있으며, AI는 로컬 개발 서버의 구성과 실행을 돕는다. 전용 Chromium 기반 앱은 구현 후보이며 구체적인 제품 기반은 아직 확정하지 않았다.

기본 흐름은 `로컬 편집 → 로컬 서버에서 실행·검증 → 빌드·배포 → 운영 실행`이다. 운영에서는 직접 편집하지 않는다. 로컬 변경만으로 운영 코드나 DB가 바뀌어서는 안 된다.

빌드는 편집용 metadata의 객체·데이터 연결을 실행 코드와 쿼리로 변환한다. 운영에는 편집기와 편집용 metadata JSON에 의존하지 않는 결과물을 배포하는 것이 목표다. 운영 DB의 구조를 설명하는 코멘트는 별도로 함께 배포한다. 구체적인 빌드·배포 구현은 후속 과제다.

## 2. Direct Manipulation First

> 설명할 필요가 없는 것은 설명하지 않는다.

텍스트는 직접 고치고, 버튼은 직접 옮기고, 크기는 직접 바꾼다. 단순한 변경마다 AI에게 설명하고 기다릴 필요가 없어야 한다. 데이터·로직·여러 구성요소에 걸친 복잡한 변경에는 AI의 도움을 받는다.

목표로 하는 조작 흐름은 다음과 같다.

- `⌘+클릭`으로 객체 선택, 드래그로 이동, 핸들로 크기 변경, 더블클릭으로 텍스트 수정.
- Inspector에서 정렬, 간격, 폰트, 색상, padding과 데이터 연결을 바로 수정.
- 여러 객체를 함께 선택해 이동·정렬하고 결과를 즉시 확인.
- 테이블·필드·관계를 직접 다루고, 데이터 필드와 화면 객체를 연결.

직접조작은 반응형 레이아웃의 의미를 보존해야 한다. 이동을 무조건 절대좌표 변경으로 저장하기보다 Flex 순서, Grid 배치, 간격, 정렬 등 적절한 표준 구조로 번역하는 방향을 검토한다.

## 3. 제품·비용·생태계 원칙

- **브라우저 실행:** 완성된 프로그램은 웹브라우저에서 실행되어야 한다.
- **합리적인 구독:** 구독제로 운영하되 사용자 수가 늘어날수록 월 1인당 비용이 줄어드는 구조를 지향한다. 총 월요금이 반드시 감소한다는 뜻은 아니며, 구체적인 가격표와 과금 단위는 아직 정하지 않았다.
- **기여 생태계:** Spring처럼 개발자의 기여로 플랫폼이 발전하는 생태계를 지향한다. 라이선스와 기여 운영 방식은 후속 설계에서 정한다.
- **기존 보안규칙 준수:** 기존 개발도구와 검증된 웹·DB 기술의 보안규칙을 따른다. UI 적용속도를 이유로 인증·권한·데이터 보호를 생략하지 않는다.
- **UI 적용속도에 집중:** 모든 개발 기술을 다시 만들기보다 생각한 UI를 수정하고 확인하는 시간을 줄이는 데 우선 집중한다.
- **필요한 만큼의 구조:** 문제의 규모에 맞는 구조로 시작하고 실제 필요가 생기면 확장한다. 단순한 시작이 향후 확장이나 직접 접근을 막아서는 안 된다.

## 4. RELOADED는 통역가다

> 기존 표준 기술을 유지하면서 사람의 의도와 실행 결과 사이의 번역·배포 격차를 줄인다.

RELOADED는 웹, 백엔드, DBMS 사이에서 해석·연결·시각화·변경을 돕는 개발 계층이다. DBMS의 Primary Key(PK), Foreign Key(FK), Auto Increment, UUID, 트랜잭션, 원자성, 동시성 제어, 격리 수준, 잠금, 제약조건과 인덱스를 그대로 받아들인다. 이 기능들을 독자적인 규칙으로 대체하지 않는다.

고급 개발자는 필요할 때 SQL, 스키마, 인덱스, FK 정책, 실행 계획, 트랜잭션 설정과 DBMS 고유 기능을 **핀셋 수정**할 수 있어야 한다. 추상화는 접근을 쉽게 하는 수단이며 아래 계층으로 내려가는 길도 유지한다. 직접 수정한 물리 구조와 metadata의 정합성을 어떻게 확인하고 다시 연결할지는 구현 단계에서 검증한다.

현재 방향에서 **Oracle은 RELOADED 지원 대상에서 제외**한다. 이는 비용과 지원 복잡성에 대한 프로젝트의 선택이며, Oracle의 모든 제품에 관한 가격·라이선스 사실을 단정하는 주장은 아니다. 기본 DBMS와 나머지 지원 범위는 별도 결정한다.

## 5. 핵심 KPI

> **생각한 것이 실제 화면에 나타나기까지 걸리는 시간.**

이 시간을 RELOADED의 통역 성능이자 핵심 성능지표로 삼는다. 새 기능과 구조를 검토할 때도 이 시간을 줄이는지 판단한다.

프로토타입에서는 텍스트 수정, 객체 이동, 필드 연결 같은 대표 작업별로 의도·작업의 시작 기준부터 실제 화면에서 결과를 확인하기까지 측정한다. 사람의 조작·설명 시간과 시스템의 반영 대기시간을 함께 살핀다. 측정 시작 기준과 목표 수치는 검증 과정에서 구체화한다.

개발 성능과 실행 성능은 구분한다. 개발 성능은 `생각 → 실제 화면`, 실행 성능은 `최종 사용자 행동 → 화면 반응`에 걸리는 시간이다.

## 6. Database / Table / Field의 이름과 Identity 분리

사람이 읽는 이름과 시스템이 참조하는 안정적 코드·Identity를 분리한다. Database, Table, Field 모두 같은 원칙을 적용한다. 이름·용도·매핑의 정본은 별도 관리 테이블에 저장하고, 로컬 편집에서는 이 정보를 metadata JSON으로 사용한다.

다음은 개념 예시이며 확정된 JSON 스키마가 아니다.

```json
{
  "D001": {
    "name": "영업관리",
    "tables": {
      "T001": {
        "name": "고객",
        "fields": {
          "F001": { "name": "고객명", "type": "text" },
          "F002": { "name": "전화번호", "type": "text" }
        }
      }
    }
  }
}
```

`영업관리 → 통합영업관리`, `고객 → 거래처`, `전화번호 → 휴대전화`로 이름을 바꾸어도 `D001.T001.F002`의 Identity는 유지한다. 이 매핑을 사용하는 내부 UI 연결·계산·쿼리는 표시 이름 변경으로 참조가 끊기지 않도록 한다.

테이블 코드는 해당 데이터베이스 안에서, 필드 코드는 해당 테이블 안에서 **전진 생성(단조 증가)**한다. 삭제한 코드는 재사용하지 않는다. 삭제 후 같은 이름으로 만든 필드도 새로운 Identity를 가진다. 마지막 발급 번호나 삭제 이력을 보존하여 과거 참조가 새로운 객체에 잘못 연결되지 않게 한다.

RELOADED의 객체 Identity와 실제 데이터 레코드의 PK는 별개다. `T001.F002`는 개발 대상 필드를 식별하고, 해당 필드에 저장된 레코드 키는 기존 DBMS의 PK/FK 규칙을 따른다. metadata Identity는 PK, Auto Increment 또는 UUID를 대체하지 않는다.

표시 이름·짧은 코드·물리 DB 이름을 매핑하는 구조를 유지하여 기존 DB의 이름까지 반드시 코드로 바꾸도록 강제하지 않는다. 프로젝트 복사·가져오기·Git 분기 병합에서 코드 충돌을 다루기 위한 별도 영구 ID(UUID 등)와 발급 조정 방식은 검토 과제다.

### 관리 테이블, Git metadata, 운영 DB 코멘트

RELOADED가 코드로 생성한 테이블·필드는 운영에서도 같은 코드로 유지한다. 코드의 의미를 잃지 않도록 다음 구조를 사용한다.

| 구분 | 역할 |
| --- | --- |
| 별도 관리 테이블 | Database/Table/Field의 Identity·코드·이름·용도·타입·물리 매핑을 보관하는 정본 |
| 로컬 metadata JSON | 정본을 바탕으로 편집·참조에 사용하는 표현 |
| Git metadata | 검토·비교·복원할 수 있도록 저장한 버전별 metadata 스냅샷 |
| 운영 DB 코멘트 | 배포 버전의 이름·용도를 DB 자체에서 확인하기 위한 설명 |

예를 들어 `T001`의 코멘트는 `고객 — 고객 기본정보`, `T001.F002`의 코멘트는 `고객명 — 고객 표시 이름`처럼 작성한다. 코멘트에는 실제 고객 데이터나 비밀값을 넣지 않는다. 구체적인 관리 테이블 스키마와 DBMS별 코멘트 반영 방식은 후속 설계에서 정한다.

로컬 편집은 관리 테이블과 metadata에 일관되게 반영하고, 검증된 버전의 metadata를 Git에 기록한다. Git에서 과거 버전을 복원하거나 분기를 병합할 때도 해당 스냅샷과 관리 테이블을 맞춘 뒤 결과물을 생성한다. JSON과 관리 테이블을 서로 독립적인 정본으로 운영하지 않는다. 저장·병합·복원 절차는 구현 시 검증한다.

배포 결과의 코드·DB 변경·코멘트는 동일한 검증 버전에서 생성한다. 개발용 관리 테이블 전체를 운영에 복제할지는 아직 정하지 않았으며, 운영 앱이 편집용 metadata를 읽지 않는 원칙과 DB 코멘트의 보존은 함께 유지한다.

다른 AI와 개발자는 테이블을 분석할 때 **테이블·필드 코멘트를 먼저 확인하여 용도를 파악**한다. 실제 타입·PK/FK·제약조건과 대조하고, 코멘트가 없거나 모순되면 해당 배포 버전의 Git metadata를 확인한다. 코드명만으로 업무 의미를 추측하지 않는다. 이 절차는 저장소의 [AGENTS.md](../AGENTS.md)에 명시한다.

## 7. 사람이 읽는 쿼리와 내부 참조

기존 표준 쿼리의 의미를 유지하면서 테이블·필드 코드를 사람이 읽기 좋은 이름으로 변환해 보여준다. 이름 변경을 단순한 문자열 치환으로 처리하기보다 어떤 객체를 참조하는지 보존하는 방향이다.

가능한 구현 흐름은 `사람이 읽는 SQL → stable ID 기반 AST(구문 트리) → DBMS별 실행 SQL`이다. 이는 검토 가능한 구현안이며 새로운 쿼리 언어를 만들기로 확정한 것은 아니다.

이름 해석 범위, 같은 이름의 구분, DBMS별 SQL과 고유 기능의 처리는 검증이 필요하다. 외부 API나 외부 SQL 사용자가 이름을 계약으로 쓰는 경우까지 metadata만으로 자동 보호되지는 않는다. 내부 이름 변경과 외부 계약 변경을 구분한다.

## 8. 데이터 구조 변경에 유연하게 반응

구조 변경은 개발 과정의 정상적인 상태로 다룬다. 영향 범위를 구분하여 한 부분의 변화 때문에 화면 전체가 실패하지 않게 한다.

| 변경 | 의도한 동작 |
| --- | --- |
| 표시 이름 변경 | metadata 이름을 갱신하고 안정적 참조를 유지한다. |
| 표시할 필드 없음 | 해당 표시를 생략한다. |
| 새 필드 추가 | 값이 없으면 비어 있는 상태로 표시할 수 있다. |
| 뷰 관계 변경·유실 | 관계에 의존해 더 이상 표시할 수 없는 뷰 또는 영역을 표시하지 않는다. |
| 계산 입력 필드·관계 경로 유실 | 계산 의존성을 확인해 `필드 유실`로 알린다. |
| 타입 변경 | 가능한 값은 변환하고, 변환 불가 값은 `???`로 표시한다. |

여기서 화면 표시를 위한 관계와 DBMS의 FK·무결성 제약은 구분한다. 뷰를 숨기는 처리가 FK를 제거하거나 트랜잭션 규칙을 무시한다는 뜻은 아니다.

예를 들어 텍스트를 숫자로 바꿀 때 `"123"`, `"45.7"`, `"ABC"`는 화면에 각각 `123`, `45.7`, `???`로 표현한다. 변환 불가 값 하나 때문에 레코드나 프로그램 전체를 실패시키지 않는다. `???`는 표시 상태이며 숫자 컬럼에 그 문자열을 저장하겠다는 의미는 아니다.

텍스트·숫자·날짜·시간·타임스탬프의 변환 규칙, 원본 값 보존, 변환 실패 상태와 계산 전파 방식은 후속 설계에서 정한다. 화면의 유연한 표시와 실제 저장 타입 변경을 구분하고, NOT NULL·UNIQUE·FK 등 DBMS 제약 및 트랜잭션의 의미는 유지한다.

## 9. Git/GitHub에 결정 이유까지 기록

코드와 함께 개발 철학, 설계 선택, 선택한 이유와 검증 결과를 기록한다. 문서는 논의를 따라 갱신하며 확정 방향, 구현 후보, 아직 확인하지 않은 가정을 구분한다.

코드·이름·용도·타입·매핑 등 metadata도 해당 코드 변경과 함께 버전 관리한다. 실제 업무 레코드, DB 접속 비밀번호, 토큰, 복호화 키는 metadata에 포함하지 않는다.

### 민감한 metadata와 복호화 키의 분리

업체의 보안 정책상 스키마 설명 자체가 민감하면 metadata 파일을 암호화해 Git에 기록할 수 있다. 이 경우 평문 metadata 대신 암호문을 추적하고, 복호화 키 또는 암호는 Git 파일·커밋 이력과 분리해 **GitHub Actions Secrets** 등 지정된 비밀 관리 수단에 보관한다. Git 자체에는 Secrets 저장 기능이 없다.

GitHub Actions에서 배포할 때는 권한이 있는 작업에만 키를 전달하여 필요한 metadata를 복호화한다. 저장소를 clone한 로컬 AI에 Actions Secret이 자동 전달되는 구조는 아니다. 로컬 작업에는 업체가 허용한 별도 키 전달·보관 경로가 필요하다.

복호화 키와 복호화한 민감한 원문을 로그·공개 빌드 산출물·브라우저 번들에 포함하지 않는다. 암호화 파일에서 복호화된 모든 내용이 GitHub 로그에서 자동으로 가려지는 것은 아니다. 운영 DB 코멘트는 DB 접근 권한 범위에서 읽히므로, Git 파일 암호화가 코멘트 접근까지 보호하는 것으로 간주하지 않는다.

이 절은 선택 가능한 보관 정책이며 암호화 방식, 키 발급·회전, CI 설정이 구현되었다는 뜻은 아니다. 참고: [GitHub Actions의 Secrets 사용 및 암호화 파일 보관](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

일상적인 개발 흐름은 `직접 수정 또는 AI 수정 → 즉시 확인 → 의미 있는 상태에서 Git commit`을 지향한다. Git의 기록·비교·분기·복원 장점을 유지하되 매번 개발 흐름을 끊지 않는 경험을 목표로 한다. 왜 만들었는지에 관한 기록은 장기적인 프로젝트 이해와 향후 집필 자료로도 남긴다.

## 10. CHECK-01 — 직접 편집·metadata 계층의 실행 성능 비용

**상태: 미검증. 프로토타입에서 측정할 과제.**

> 직접 편집·metadata 계층이 최종 HTML/CSS/JS와 DOM 실행 성능에 어느 정도 overhead를 발생시키는가?

코드 길이뿐 아니라 전송량, 해석·실행 작업량, DOM 수, 스타일·레이아웃 계산, 렌더링과 메모리를 측정한다. DOM은 브라우저가 HTML을 바탕으로 메모리에 만들고 관리하는 객체 구조다. DB 레코드 수, 개발 객체 수, 실제로 화면에 생성한 DOM 수는 서로 다른 측정값이다.

검증 계획:

1. 같은 화면·데이터·동작을 갖춘 표준 구현, RELOADED 개발모드, RELOADED 운영 빌드를 비교한다. 브라우저·기기·네트워크·측정 조건을 기록한다.
2. 객체 100 / 1,000 / 10,000개 조건에서 전체 객체 수와 실제 DOM 수를 각각 기록한다.
3. HTML/CSS/JS 전송 크기, CSS 규칙 수, JS 해석·실행 시간, 초기 렌더링, 조작 후 반응시간, 스타일 재계산·레이아웃 비용, 메모리를 측정한다.
4. 직접 선택·Drag·Resize·Inspector·Binding 표시·AI Context·편집 History 같은 개발 전용 기능을 운영 빌드에서 제외하는 분리가 작동하는지 확인한다. 운영에 필요한 실제 기능·연결 정보는 유지한다.
5. Flex/Grid·컴포넌트·CSS 클래스 재사용과 목록 가상화의 효과를 비교한다. 10,000개 객체나 레코드가 있다고 모두 DOM에 올릴 필요는 없다.
6. DOM 요소와 stable object ID, 컴포넌트·소스 사이의 연결 비용을 측정한다. 기준 구현 대비 차이를 기록하고 병목과 허용 기준을 정한다.

측정 전에는 실행 부담이 없거나 일반 웹 앱과 동일하다고 단정하지 않는다. 개발 속도를 높이는 계층이 최종 사용자 경험에 미치는 비용을 수치로 확인한다.
